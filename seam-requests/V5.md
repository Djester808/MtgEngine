# V5 — what the runner and the interpreter owe the four new members

Four vocabulary additions, all optional members with the old behaviour as their default, so
`IrVersion` is unchanged and every card file and scenario file written before this wave reads
unaltered (`ScenarioVocabularyTests.A_scenario_written_before_these_members_still_reads`). None of
them does anything until the folder named below reads it; until then a scenario that carries one is
accepted, round-trips and is ignored, which is the honest state and not a silent failure.

## 1. `ScenarioSetup.AutoAnswer` — owed by `MtgEngine.Rules/Scenarios` (P10)

```csharp
public sealed record ScenarioSetup(…, int Turn = 1, bool AutoAnswer = false);
```

P9's line, landed as written. What P10 does with it:

- `ScenarioRunner` reads `scenario.Setup.AutoAnswer` and the `ScenarioRunner(Game, bool autoAnswer)`
  constructor flag goes; `VerifyCommand` stops passing `true` and the smoke generator sets
  `AutoAnswer: true` on the setup it builds instead. That is the whole point of moving it: today
  every scenario in a run is auto-answered or none is, and a card file cannot hold one hand-written
  scenario that answers itself beside a generated one that does not.
- **Keep the "a scenario with an `AnswerStep` of its own is left alone" rule** as a belt: the
  current runner infers the opt-in that way (`ScenarioRunner.cs:40`), and a generated scenario that
  later grows an `AnswerStep` should still lose the automatic answers rather than have them
  interleaved. `AutoAnswer && !scenario.Steps.OfType<AnswerStep>().Any()` reads the same with the
  flag off the constructor.
- `ScenarioAnswers.FirstLegal` is unchanged; it is the answer, not the opt-in.

The doc comment on the field is the translator- and generator-facing statement of who answers, and
it is in the generated schema, so the generation stage's prompt gets it for free.

## 2. `CastStep.CostObjects` and `ActivateStep.CostObjects` — owed by `MtgEngine.Rules/Scenarios` (P10)

```csharp
public sealed record CastStep(…, string? AlternativeCost = null, IReadOnlyList<string>? CostObjects = null);
public sealed record ActivateStep(…, IReadOnlyList<string>? CostChoices = null, IReadOnlyList<string>? CostObjects = null);
```

`ScenarioRun.Commands` maps them through its `Object(...)` alias resolution into
`CastSpell.CostObjects` and `ActivateAbility.CostObjects`, which have been on the commands since
wave 5 ("Seam decisions after wave 5", E3c). That is P9's own half and lands the same day. The
casting system already reads the command field (E3d, wave 6), so Village Rites and Culling the Weak
should verify as soon as the mapping exists — nothing further is owed by the engine.

Names in the list are aliases first, card names second, exactly like `Targets`.

## 3. `ManaPoolIs` and `AttachedToIs` — owed by `ScenarioExpectations.Check` (P10)

```csharp
public sealed record ManaPoolIs(string Player, string Mana) : Expectation;
public sealed record AttachedToIs(string Card, string To) : Expectation;
```

**`AttachedTo` was not available.** `MtgEngine.Cards/Selectors.cs:203` already has
`AttachedTo(Selector To) : Predicate` — the filter a card's own text uses ("Auras attached to it").
Two records of that name do not compile, and `NameTableTests.No_discriminator_is_used_twice_across_bases`
forbids the discriminator even if they did. `AttachedToIs` follows `TappedIs` / `CountersAre` /
`TypesAre`, which is the naming the other expectations already use. P9's generator and any prompt
text that names the expectation need the changed spelling; `ManaPoolIs` is exactly as requested.

Both are plain `string` for player and card, not `PlayerRef` / `CardRef`: every expectation in
`Scenarios.cs` names players and cards by alias-or-name as a string, and `PlayerRef` is the card
vocabulary's "you / target opponent / each player" selector, which is not what an expectation means.
The brief's shorthand and the file's convention disagree, and the file wins — a `PlayerRef` here
would be the only one in `Expectation` and would have to be resolved by a different code path.

The two arms:

- `ManaPoolIs` compares the pool as a **bag of symbols**, not a sequence: parse `Mana` the way a
  mana cost is parsed and compare totals per symbol, so `"{G}{G}"` and a pool that gained the two
  greens in either order both pass (CR 106.4). The empty string is an empty pool. Restricted mana
  (`ManaPool.Restricted`, wave 6) counts as the symbol it is — an expectation that needs to see the
  restriction is a second record, not a spelling of this one.
- `AttachedToIs` reads the attachment off the permanent (`GameObject.AttachedTo`) and compares the
  resolved object, so it fails rather than passes when the Aura is in a graveyard. It replaces the
  `InZone(card, Battlefield)` the Aura generator asserts today, which is true only for as long as
  CR 704.5m takes to bury an unattached Aura.

Neither expectation says anything about **the CR 303.4f gap P9 §3 names** — an Aura cast at a legal
object still resolves attached to nothing. `AttachedToIs` makes that failure legible; it does not
fix it, and Song of the Dryads and Kenrith's Transformation stay failing until the casting or zone
system carries the spell's target onto the permanent. That is still E3d/E1b, not this record.

## 4. The Ring's emblem — nothing is owed; the shape was already there

`CreateEmblem(EmblemSpec Emblem, PlayerRef? Who = null)` and
`EmblemSpec(string Name, IReadOnlyList<Ability> Abilities)` already exist in `Effects.Verbs.cs`.
E9e's "`Emblem` is not an `Effect`" is out of date — what is actually missing is nothing, and adding
a second emblem record for the Ring would be the wrong answer.

**The decision, written down because it is a refusal and not an omission: `RingTemptsYou` carries no
`EmblemSpec` and must never be given one.** CR 701.54b prints the emblem's four abilities in the
*rulebook*. No card prints them: a card says "the Ring tempts you" and nothing else, and which of
the four abilities the emblem has depends on how many times that player has been tempted, which is
game state. Spelling them into a card file would put engine data in `cards/` — the plan's first rule
inverted — and would drift the moment Wizards rewords one. So:

- The engine supplies the emblem and its abilities from the rules, the way it supplies the monarch's
  and the initiative's, when it runs the `RingTemptsYou` arm (CR 701.54a and c are already there).
  **That is the one thing still owed, and it is `Rules/Interpreter`'s (E9-series), not the
  vocabulary's.** Until it lands a card that tempts is not `Verified`, which is E9e's own reading and
  stands.
- `CreateEmblem` stays for the emblems a card's own text prints — a planeswalker's ultimate,
  CR 114.2. Its doc comment now says so, and points at `RingTemptsYou` for the other kind.
- `ScenarioVocabularyTests.The_Ring_carries_no_emblem_of_its_own` asserts `RingTemptsYou` has
  exactly one member, so a later pass cannot quietly add the spec back.

## Not asked for

- **`ManaPoolIs` for a restricted pool.** `ManaPool.Restricted` landed in wave 6 and nothing in the
  pilot needs to assert it yet. One more expectation when a card does; not a flag on this one.
- **`CardRef`/`PlayerRef` in expectations.** See §3 — it would be a change to every expectation in
  the file, and the string is what the runner resolves.
- **An `AttachedToIs` that also asserts the attachment is legal.** CR 303.4f legality is the
  engine's job and asserting it here would let a scenario pass on an illegal attachment the SBAs are
  about to undo.
