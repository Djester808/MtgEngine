# P9 — seam requests

Measured with `dotnet run --project MtgEngine.Cards.Pipeline -- verify cards` in this worktree over
a clean `cards/`: **66 verified, 4 failed, 16 with no scenarios, 1 crashed** (`engine:0813f37cabbabed6`),
against 57 / 6 / 24 / 0 on the tip I branched from. Every item below is one of the four or the one,
and none is in a file I own.

## 1. `ScenarioSetup.AutoAnswer`, or an `AnswerFirstLegalStep` — `MtgEngine.Cards/Scenarios.cs`

The opt-in landed on the runner rather than in the scenario, because `Scenarios.cs` is the V-series'
file: `ScenarioRunner(Game game, bool autoAnswer = false)`, and `VerifyCommand` passes `true`. That
works, but the opt-in belongs to the scenario and not to whoever built the runner, so a card file
that carries a hand-written scenario cannot say "answer this one for me" while a sibling says "I
make my own choices". Today the runner infers it: auto-answering is switched off for any scenario
that carries an `AnswerStep` of its own. The line I would add:

```csharp
public sealed record ScenarioSetup(
    IReadOnlyList<PlayerSetup> Players,
    string ActivePlayer,
    Step StartAt = Step.PrecombatMain,
    int Seed = 1,
    int Turn = 1,
    bool AutoAnswer = false);
```

`ScenarioRunner` would then read `scenario.Setup.AutoAnswer` and the constructor flag would go. The
answering itself is `MtgEngine.Rules/Scenarios/ScenarioAnswers.cs` and stays mine.

## 2. Two expectations a generated scenario has to state as an event instead

`Expectation` has no member for a mana pool or for an attachment, so two generators assert the event
the engine logged rather than the position it left:

- `AddMana` expects `EventLogged("ManaChanged")`. It would rather say `ManaPoolIs(string Player, string Mana)` —
  the smoke setup already stocks a deep pool, so a total is the only honest reading.
- an Aura expects `InZone(card, Battlefield)`, which is true only because CR 704.5m buries an
  unattached one. `AttachedTo(string Card, string To)` would say what is actually meant.

Both are one record plus one arm in `ScenarioExpectations.Check`, which is mine; the records are not.

## 3. An Aura is cast at a legal object and still is not attached (CR 303.4f)

The two Aura failures are no longer the scenario's fault. `SmokeScenario` now reads the
`KeywordAbility(Enchant)` filter, places what it describes and casts the Aura at it, and the pipeline
test proves the step carries the target:

```
FAILED Song of the Dryads (enchant permanent), Kenrith's Transformation (enchant creature): InZone was Graveyard
```

So the spell resolves onto the battlefield attached to nothing and the state-based action buries it.
CR 303.4f: "the Aura enters the battlefield attached to the object or player it was cast at" — the
casting or zone system has to carry the spell's target onto the permanent as `AttachedTo` when an
Aura resolves. That is E3d/E1b territory. Two cards, and both verify the moment it lands.

## 4. `CastStep` cannot name the permanent a printed sacrifice cost eats (CR 601.2f)

`CastSpell.CostObjects` exists on the command as of wave 5, but `CastStep` — the scenario's side of
it — does not, so a generated scenario cannot supply the body:

```
FAILED Village Rites, Culling the Weak: The engine refused CastSpell: There are not enough permanents to sacrifice. (601.2h)
```

The board can place one (`SmokeBoard.Place`); it has nowhere to say which. The line:

```csharp
public sealed record CastStep(string Player, string Card, IReadOnlyList<string>? Targets = null, int? X = null,
    IReadOnlyList<int>? Modes = null, IReadOnlyList<string>? CostChoices = null, string? AlternativeCost = null,
    IReadOnlyList<string>? CostObjects = null) : ScenarioStep;
```

with `ScenarioRun.Commands` mapping it through `Object(...)` into `CastSpell.CostObjects` — that half
is mine, and lands the same day the field does. `ActivateStep` wants the same field for the same reason.
