# E6 — triggers

## 1. `events.txt` gains one line (blocking the full suite)

`TriggerFired` is a new `GameEvent` in `MtgEngine.Rules/Triggers/TriggerFired.cs`. `EventLogTests`
compares the assembly's events to `tests/MtgEngine.Rules.Tests/events.txt`, which E6 does not own,
so that test is red until this line is added between `SpellCast` and `TurnBegan`:

```
TriggerFired
```

## 2. The stack object cannot carry what the trigger triggered on

The brief asks for the trigger's stack object to carry the triggering objects under the key
`triggering`. Nothing on the stack can hold them today: `GameObject` has no memory, and
`StackEntry` (`MtgEngine.Rules/State/GameObject.cs`) carries targets, modes and X but no remembered
objects. Requested:

```csharp
public sealed record StackEntry(
    ...,
    ImmutableDictionary<string, ImmutableList<ObjectId>>? Remembered = null,
    ImmutableDictionary<string, ImmutableList<PlayerId>>? RememberedPlayers = null);
```

Until then the firing is recorded on the `TriggerFired` event instead: it names the stack object,
the source, the ability index, the triggering objects and the triggering player, and
`TriggerSystem.Triggering` is the key E9 should read them back under. That is enough to replay and
to assert in tests, but E9 cannot build an `EffectContext` from the stack object alone — it has to
find the `TriggerFired` for it in the log. One field on `StackEntry` removes that.

## 3. `ObjectMoved` does not say where the object came from

`ObjectMoved(ObjectId From, GameObject To, int Position)` carries the new object but only the id of
the old one, so a trigger that looks back (CR 603.10) has nothing to match a filter against. E6
rebuilds the departed object from `To` plus `GameState.History.LeftBattlefield`, which is exact for
"did it leave the battlefield" and approximate for what it was: the restored object keeps `To`'s
definition, owner and `InitialController`, so a creature that changed control before it died looks
like its owner's. Two consequences worth the coordinator's decision:

- `ZoneChange` with a `From` that is not `Battlefield` cannot be verified at all and never matches
  today. "Whenever a card is put into your graveyard from your hand" is inert.
- Requested: `ObjectMoved` carries the old `GameObject`, not just its id — `ObjectMoved(GameObject
  From, GameObject To, int Position)` — or a `Zone? FromZone` at minimum. This is the same seam E1
  was told would land in wave 2 with the leaves-the-battlefield triggers (DECISIONS, row 3), and
  this is that landing.

## 4. Ordering more than one trigger stops the game rather than queueing

CR 603.3b lets each player order their own triggers. E6 puts every trigger on the stack in APNAP
plus collection order and, when one player has more than one, raises a `PendingChoice` of kind
`trigger-order` (`TriggerSystem.OrderChoice`) whose options are the stack objects. The answer is a
reorder of the stack, which `ZoneReordered` already expresses, so E13 needs no new event — but the
choice does halt everything after it until it is answered, which is the known "unanswered question
stalls the game" shape. If the coordinator would rather the default order stand silently until a
player asks to change it, say so and the `ChoiceRequested` comes out in one line.

## Not requested, recorded as gaps

`BecomesTarget`, `AbilityActivated`, `Scries`, `Surveils`, `Mills`, `Transforms`, `TurnsFaceUp`,
`Cycles`, `SpellCountered`, `Fights`, `Exerted`, `Crewed`, `Explores`, `ChapterReached`,
`LevelReached`, `RoomUnlocked`, `DieRolled`, `CoinFlipped`, `Voted`, `RingTempted`,
`BecomesMonarch`, `TakesInitiative`, `PhasesOut`, `PhasesIn`, `Regenerated`, `Kicked`, `Foretold`,
`Investigated`, `EnergyPaid`, `DungeonCompleted`, `Learns` and `CommanderCast` have no arm, because
no event in `Events/GameEvent.cs` names any of them. Each needs an event from the subsystem that
performs the action before the trigger can match one; they return "no match" rather than throwing so
a game does not stop on a card that has one.
