# R4 — the runner calls the one reading of CR 605.1a, and stops reporting a status a library card does not have

Wave 27. Four tests in `tests/MtgEngine.Rules.Tests/ScenarioRunnerTests.Wave27.cs`; the
`ScenarioRunnerTests` anchor is green (52 passed, 48 before). **No seam moved and no schema
changed** — `MtgEngine.Cards/Scenarios.cs` was not touched, so nothing needs regenerating this box.

## 1. `IsManaAbility`/`CouldAddMana` are gone from the runner (E5k § 4 ask 1)

`ScenarioRun.ManaAbilityIndex` now asks `MtgEngine.Rules.Query.ManaAbilities.Is(ability)` and the two
private copies in `ScenarioRunner.Mana.cs` are deleted. The runner was copy two of three: it checked
"could add mana" and "not a loyalty ability", asserted the no-target criterion held by construction
because a `TapForManaStep` announces no targets — which is a claim about the *step*, not about the
*ability* the step counts — and never checked the fourth criterion at all.

**Proved by mutation, not by the suite going green**: swapping `ManaAbilities.Is` back for
`ManaAbilities.CouldAddMana(ability.Do, null)` (the two-criterion reading, near enough) fails exactly
the two 605.1a tests here and nothing else in the anchor (`Failed: 4, Passed: 48` with the CR 110.5d
mutation of § 2 applied in the same run; the two halves are disjoint tests).

The test that carries it is not a predicate unit test — it is a scenario. A fake artifact prints
`{T}: Add {G}. Draw a card.` first and `{T}: Add {U}.` second, and `TapForManaStep(AbilityIndex: 0)`
has to reach the **second**: the colour in the pool, plus a hand that is still empty and a library
still at two cards, is what says the runner counted mana abilities the way the rule does. The
sibling test is the same first ability with nothing behind it — no mana ability at all, refused with
605.1a.

**Ask (E-series, unchanged from E5k § 4 ask 2):** `CastingSystem.ManaAbilities` is now the last copy,
and it is the one that decides what resolves without using the stack (CR 605.3a). Until it calls
`ManaAbilities.Is` the runner and the casting system can still disagree — the runner will now decline
to *count* an ability the casting system would still resolve manalessly. No corpus card turns on the
gap today (the runner's refusal comes first for every shape that reaches it), so this stays a
correctness debt, but it is one copy from finished.

## 2. CR 110.5d: a card off the battlefield is neither tapped nor untapped

`204b71fc` (Elixir of Immortality) failed "TappedIs was untapped". Nothing about the tap was wrong:
`{2}, {T}` was paid, and then the ability shuffled its own source into its owner's library. CR 400.7
makes that a new object, `ScenarioRun.Track` follows the scenario's name onto it (correctly — the
name has to follow the card), and `ScenarioExpectations` then read `GameObject.Tapped` off a library
card and reported "untapped".

`Tapped` is now answered honestly: an object whose zone is not the battlefield fails with the zone
and the rule — `in Library, and a card that is not on the battlefield is neither tapped nor untapped
(110.5d)`. It refuses rather than reports because CR 110.5d says the status does not exist, not that
it is false.

**This closes a silent false pass, not only a noisy failure.** `TappedIs(card, false)` about a card
in a graveyard, a library or exile *passed* before, because the field on a non-permanent reads false.
Both tests here assert the failure; the `TappedIs(card, false)` one is the mutation-proof half — with
the zone guard disabled that scenario passes outright and the test catches it.

### What P26 should generate instead (the ask)

The activation smoke generator asserts `TappedIs(card, true)` whenever the ability's cost contains
`TapSelf`. That is the right claim only while the source is still a permanent when the expectations
are checked. **Do not assert `TappedIs` when the ability's effect can move its own source out of the
battlefield.** The shapes to look for in the effect tree, each reaching `Self` (or a filter the
source matches) as what it moves:

- `Shuffle { IntoLibrary: … Self … }` — Elixir's, CR 701.20 with 400.7.
- `MoveTo`/`Destroy`/`Exile`/`Sacrifice`/`Bounce`-shaped records naming `Self`.

For those, assert the **zone the effect names** instead — for Elixir, `InZone(card, Library)` — which
is a claim about what the ability did and survives CR 400.7 intact. Keep the other expectations the
generator already writes (`Life`, `StackEmpty`); Elixir's `Life: 25` is correct and passes.

Two things to note while writing that arm:

- **`InZone` is checked against the *followed* object**, so it reads the library card and passes. The
  name-following is the runner's and needs no generator help.
- **Do not reach for "assert the tap another way".** There is no expectation record for "the tap cost
  was paid" and this box did not add one, because the honest claim for a source that left is the
  zone, not a re-spelling of a status it no longer has. If a card ever needs the tap itself asserted
  *and* the source leaves, that is a new `Expectation` on `MtgEngine.Cards/Scenarios.cs` — a schema
  change, so it is a seam ask with a regeneration, not a runner change.

A generated scenario that keeps `TappedIs(card, true)` for one of these cards now fails with a
message that names the zone, so the generator's own failure list will point at the cards that need
the new arm rather than at a status the engine got right.

## 3. Not changed, recorded so the next box does not re-derive it

- **`TappedIs` about a card that is no longer in the game at all** still comes back through
  `Object(run, key)`'s `'{key}' is no longer in the game.` failure, which is the same honest shape and
  needed no work.
- **`PowerToughness`, `CountersAre`, `HasKeywordNow` and `TypesAre` were not given the same guard.**
  Unlike status, characteristics *do* exist for a card outside the battlefield (CR 109.4 with 613.1),
  so reading them off a graveyard card is not the same defect and a blanket zone guard would be
  wrong. `AttachedToIs` already reports the zone for an unattached permanent. If a generated
  scenario is ever found asserting a *battlefield-only* characteristic about a card that left, name
  the record and the CR and it is one arm here.
