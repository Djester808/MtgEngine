Every pilot card the vocabulary can express now plays and passes. The four counted "unsupported"

## 1. The request: `ActivateStep` needs a mana colour (CR 608.2d)

P11 closed the "add one mana of any colour" arm because the colour travels with the command and a
generated scenario has no way to make it. Five cards lost their activation scenario that way.

The engine does **not** ask a question for it — the refusal is "The colour of mana to add was not
chosen", raised while the command is built, so there is no `PendingChoice` for `AnswerStep` to
answer and no `FirstLegal` that could say "W". The choice has to be on the step.

**Request** — in `MtgEngine.Cards/Scenarios.cs`, one field on the existing record:

```csharp
public sealed record ActivateStep(
    string Player,
    string Card,
    int AbilityIndex,
    IReadOnlyList<string>? Targets = null,
    int? X = null,
    IReadOnlyList<string>? CostChoices = null,
    IReadOnlyList<string>? CostObjects = null,
    string? ManaColors = null) : ScenarioStep;
```

`ManaColors` is a pool string in the runner's own spelling (`"W"`, `"WU"`) — one letter per
"of any colour" the activation adds, in the order the effect adds them; null is what every existing
step means and changes nothing. The runner passes it to the activate command as the chosen colours;
`SmokeActivation` then generates the scenario with `"W"` and asserts `ManaPoolIs`, exactly as the
cast-side `AddMana` arm already does for a fixed colour.

It is not mine to add (`MtgEngine.Cards`), and the command side is E9h's. Used only after it lands.

## 2. What the three became, and the engine gap behind one of them

- **Harrow-shaped** — two things stopped it, neither of them the search. The printed
  `SacrificeCost` was refused unless it named a *creature*, so "sacrifice a land" got no scenario at
  all; it now places whichever filler its own filter admits (`SmokeFillers.Bodies`), the same
  reading the effect-side sacrifice already used. Then `Search { UpTo: Fixed 2 }` stocked one card
  and asserted one: the board now stocks as many as the search may take and asserts where **each**
  of them went, plus the library they came out of.
- **Chord of Calling / Finale of Devastation-shaped** — `ObjectFilter.ManaValue` made the filter
  un-`Plain`, so no filler was findable. `ScenarioFiller` gained a creature at zero and one at six,
  `ScenarioFiller.ManaValueOf` reads a filler's printed cost (CR 202.3), and `SmokeFillers` compares
  it against the filter's `Comparison` — against the **announced X** when the bound is `X`
  (CR 601.2b), which the board now carries as `SmokeBoard.AnnouncedX`. The two new fillers are last
  in the findable list, so a search that names no mana value finds exactly what it found before.
- **Entish Restoration-shaped** — the question was a **search that found nothing**. The card's
  `If` arms both search for a *basic* land, the generator never reads inside an `If`, so the library
  was never stocked with one; the search offered zero options, `FirstLegal` answered with an empty
  list, and `ScenarioRun.Answer` reads an empty list as "nothing legal to say" and leaves the
  question standing — the spell never left the stack. CR 701.23b says finding nothing is a legal
  outcome, not an unanswerable question, so `ScenarioAnswers.FailsToFind` now tells the two apart
  and the runner answers with none. That is the "unanswered question stalls the game" shape, fixed
  where it belonged rather than worked around in the generator.

## 3. Two engine-side answering changes, both in `MtgEngine.Rules/Scenarios`

- `ScenarioAnswers.FirstLegal` for a search takes every option the question's **maximum** admits
  (CR 701.23a), not the first one. A search with no maximum still takes one, so nothing that ran
  before answers differently.
- `ScenarioAnswers.FailsToFind` + the one-line guard in `ScenarioRun.Answer`, above.

## 4. `Unsupported` is refused before a game starts

`VerifyCommand` walks each candidate's definition (`Linter.Walk`) and refuses any that carries an
`Unsupported` marker: it is counted under its own "unsupported" heading, the translator's `Reason`
is the log line, the file is left exactly as it is, and the reason is recorded as the first
expectation's `Error` — the same place `Crashed` puts an exception, so the dispute queue reads one
shape whatever stopped the card.

**One thing this cost.** `VerifyCommandTests` proved the crash path with a card whose definition
carried an `Unsupported` marker, because that is what made the interpreter throw. That card is now
refused before the engine sees it, so the crash path has no test any more; the test became the
unsupported test. A crash-path test needs a definition the engine throws on for some *other*
reason, or a seam that lets a test hand `VerifyCommand` a runner of its own — the latter is the
honest fix and is a request for whoever owns the command's construction next wave.
