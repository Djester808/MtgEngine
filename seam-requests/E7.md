# E7 — seam notes for the layer system

No seam had to change: `ICharacteristics`, `ActiveEffect`, `GameObject` and the vocabulary's
`ContinuousEffect` records carried everything layers 1–7 need. What follows is what the layer
system cannot answer on its own, and what each gap costs, so the coordinator can route it.

## 1. Wiring (coordinator's file, not mine)

`MtgEngine.Rules/Engine/Game.cs` still composes `new Stubs.Layers()`. The implementation is
`MtgEngine.Rules.Characteristics.LayerSystem` — parameterless, stateless, safe to share. One
line in `Subsystems.AllStubs()` (or whatever wave 1 replaces it with) switches it on.

## 2. What needs E0's query layer, and what happens meanwhile

The layer system cannot take `IQuery`: `IQuery` is documented as built on `ICharacteristics`,
so taking it here would be a cycle. It therefore carries its own small filter matcher, which is
narrower than `IQuery.Matches` on purpose. Three gaps follow from that.

- **Conditional static abilities.** `StaticAbility.While` needs `IQuery.Holds`. A static
  ability with a `While` condition is **skipped** — its effect never applies. Cards with
  "as long as" statics will read wrong until either E0's `Holds` is reachable from here or the
  interpreter re-states the condition as an `ActiveEffect` it maintains.
- **Player references beyond `You`, `EachOpponent`, `EachPlayer` and `ActivePlayer`.**
  `ControlBy` with any other `PlayerRef`, and a filter's `ControlledBy`/`OwnedBy` with any
  other, throw `NotImplementedException` naming the reference rather than guessing.
- **Filter fields the matcher does not answer**: `Also` (the `Predicate` tail), `ManaValue`,
  `Attacking`, `Blocking`, `Blocked`, `Historic`, `Outlaw`, `Spell`, `IsCommander`. A static
  ability whose filter sets one throws naming the field. Combat-dependent statics are E4's
  business anyway; the rest want either a mana-value helper on the vocabulary or the query
  layer.

The cleanest resolution, when E0 lands, is a one-way split: `IQuery` keeps the rich matcher and
takes `ICharacteristics`; the layer system keeps this narrow matcher for the filters that
static abilities use to choose what they apply to. If instead the coordinator wants one
matcher, the seam it needs is a *characteristics-free* filter interface that both can take —
say `IFilterMatch.Matches(GameState, ObjectFilter, ObjectId, Chars candidate, EffectContext)`,
where the caller supplies the already-computed characteristics. Say the word and I will state
it precisely.

## 3. Amounts arrive pre-evaluated

`ModifyPt`, `SetPt` and a filter's comparisons take an `Amount`, and the layer system evaluates
only `Fixed`; anything else throws naming the record. That is deliberate and matches CR 611.2d
and 608.2h: a variable in a continuous effect is determined once, when the effect is created.
So whoever creates an `ActiveEffect` — the interpreter (E9) — must pre-evaluate the amount and
store a `Fixed`. A `*` printed power and toughness needs the same: a `StaticAbility` marked
`CharacteristicDefining` whose `SetPt` carries the evaluated numbers, refreshed by whoever
maintains it. Layer 7a applies it; it does not compute it.

## 4. Text-changing effects and dependency are not built

`ChangeText` (layer 3, CR 612) is ignored, as the brief says. `RemoveTypes.AllCreatureTypes`
clears the whole subtype list, because which subtypes are creature types is the vocabulary's to
say and there is no subtype table yet. Dependency (CR 613.8) is not implemented: within a layer
everything is applied in timestamp order. The one place that shows is a static ability whose
filter reads a characteristic another *static* ability changes — filters are matched against
characteristics computed without the board's statics, so that gathering them cannot recurse.
Effects from resolved spells and abilities are visible to filters, which is what the example
under CR 613.9 needs.
