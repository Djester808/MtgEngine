## 1. The basic land types are generated (CR 205.3i)

`tools/gen-vocabulary.js` now emits a fourth file, `MtgEngine.Cards/Generated/LandTypes.g.cs`,
from the same rulebook line the engine's literal was copied out of:

```csharp
[RuleRef("205.3i")]
public static class LandTypes
{
    public static FrozenSet<string> Basic { get; }          // Forest, Island, Mountain, Plains, Swamp
    public static bool IsBasicLandType(string subtype);      // matched without regard to case
}
```

CR 205.3i lists all seventeen land types in one sentence and then names the basic five in a second
— "Of that list, Forest, Island, Mountain, Plains, and Swamp are the basic land types." — so that
second clause is what the generator reads. It throws if the clause is gone or names a number other
than five, so a rules release that rewords the sentence fails the generator rather than emitting a
short set. The full seventeen are **deliberately not emitted**: nothing asks for them, and a
generated set nobody reads drifts unnoticed past the next rules swap.

Sorted ordinally, matched with `OrdinalIgnoreCase`, and shaped exactly like `CreatureTypes.All` so
the two read the same way. `CreatureTypeTests.Regenerating_the_vocabulary_changes_nothing` already
compares every `*.g.cs` byte for byte and now asserts `LandTypes.g.cs` is among them, so the
committed file and a fresh generator run cannot diverge.

**Owed by E0e**: delete `MtgEngine.Rules/Query/LandTypes.cs` — the internal
`ImmutableArray<string> Basic` E0d wrote as the engine's one place for these five — and read
`MtgEngine.Cards.LandTypes` instead. Its two readers are the domain count in `Query.Amounts.cs`
and the `ObjectFilter.HasBasicLandType` clause in `Query.cs`; the set is unordered, which neither
of them cares about, and `IsBasicLandType` is the shape the filter clause actually wants. Nothing
breaks while both exist: the engine's copy is `internal` and in `MtgEngine.Rules.Query`, so the
enclosing namespace still wins inside that folder and no call site is ambiguous.

## 2. The linter

**`L017` — `ActivateStep.ManaColors` must be colour letters (CR 608.2d).** P12 landed the field as
free text in the runner's own pool spelling ("W", "WU"), and free text is exactly the value a lint
rule is owed for: a step naming `"WX"` is not refused until the runner builds the activate command,
one indirection away from the cause, and a scenario that refuses reads as a card that fails. The
rule is one letter per mana from `WUBRG`; an empty string is an error too, because "chooses
nothing" is spelled `null` and an empty one is a dropped value. This is the first check that walks
`file.ScenarioList` at all — `Linter.CheckScenarios` — so a later scenario-side value has a place
to go.

**The enchant decision is written into the linter, and it is a rule removed rather than added.**
E5d §2 asked for a pair rule warning on an `Enchant` with neither `Of` nor `OfPlayer`; the wave-9
table declined it, because neither half set is "enchant anything" and that is a real card the
engine cannot tell from a translation that dropped a filter. Recording that revealed the opposite
defect: `Enchant` was in `RequiredParameter` as needing `Of`, so **both legal shapes the decision
names were already lint errors** — "enchant player" (`OfPlayer` only) and "enchant anything"
(neither) both raised `L005`. It is out of that table now, with the decision and its reason in a
comment where the next reader of E5d will hit it before adding the rule back. Three tests hold the
three shapes clean: both set, neither set, and player only.

Nothing else in the tree asserted `L005` for `Enchant`; the pipeline's `TemplateKeywords` only ever
builds one with a filter, so no translation changes.
