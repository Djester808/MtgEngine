# E13 — seam requests

Three requests, in the order they matter. Everything else E13 needed already existed:
`PendingChoice`, `ChoiceOption`, `ChoiceContext`, `ChoiceRequested`, `ChoiceAnswered` and
`AnswerChoice` were enough to validate and record an answer without touching a seam.

---

## 1. Hoist `IResumable` into `Engine/Seams.cs` and let the interpreter implement it

**Why.** Seven of the eleven kinds (`trigger-order`, `replacement-order`, `may`, `value`,
`search`, `scry`, `targets`) are questions a *card* asked, not a rule the choice system
performs. The choice system must not know what an effect was in the middle of doing — that is
the interpreter's. So resumption for those kinds is a hand-back through one interface.
Resumption is by kind and by locator, never by a captured continuation: a continuation cannot
be replayed from the log, and CR 101.4's "the game waits" has to survive a reload.

E13 declared this in `MtgEngine.Rules/Choices/Resumption.cs` and dispatches through it today.
The request is to move the interface (not the record, which can stay where it is if you
prefer) to `Engine/Seams.cs`, add it to `Subsystems`, and have E9's interpreter implement it.

Exact C# as it stands in `Choices/Resumption.cs`:

```csharp
/// <summary>
/// An answered question handed back to whoever asked it. Everything the asker needs is here:
/// the kind it asked under, who answered, the options they chose (not just their ids, so the
/// object or player behind each one travels with it) and the <see cref="ChoiceContext"/> that
/// located the asking — the source, the ability index and the path inside the effect tree.
/// </summary>
public sealed record Resumption(
    string Kind,
    PlayerId Player,
    ImmutableList<ChoiceOption> Chosen,
    ChoiceContext Context);

/// <summary>
/// The seam a choice resumes through when the question came from a card rather than from a
/// rule the choice system performs itself. The interpreter implements it: it is the only
/// subsystem that knows what an effect was in the middle of doing, and the
/// <see cref="ChoiceContext"/> is how it finds that place again after the answer.
/// </summary>
public interface IResumable : ISubsystem
{
    Outcome Resume(GameState state, Resumption resumption);
}
```

**Wiring.** `ChoiceSystem`'s constructor is
`ChoiceSystem(IZoneSystem zones, ITurnSystem turn, IResumable? interpreter = null)`. The third
argument is optional so the coordinator can compose it before E9 lands; when it is null a
`UnbuiltResumable` throws `NotImplementedException("interpreter resumption is not built yet:
wave 2, agent E9.")`, the same shape as `Engine/Stubs.cs`. Once E9's interpreter implements
`IResumable`, the wiring is:

```csharp
var choices = new Choices.ChoiceSystem(zones, turn, interpreter);
```

and `Subsystems.Wave2()` passes the same interpreter instance to both `Interpreter` and
`Choices`.

**Contract for E9.** `Context.EffectPath` is the locator the interpreter set when it raised the
question; the choice system copies it back untouched. `Chosen` is in the order the player
answered, which is the order the rules mean whenever a kind says "in any order"
(`trigger-order`, `replacement-order`, `scry`).

## 2. `ITurnSystem` needs an opening step that raises the mulligan declaration (CR 103.5)

**Why.** `ITurnSystem.Begin` says "mulligans are the choice system's; this begins turn 1", but
nothing raises the first declaration, so a game can never take one. E13 answers a `mulligan`
choice and drives every later round of the loop itself — after a mulligan it raises the next
declaration, and after a keep it raises the bottoming question — but the *first* one has to
come from the turn system, before turn 1 begins.

Proposed, on `ITurnSystem` in `Engine/Seams.cs`:

```csharp
/// <summary>
/// CR 103.4–103.5: before the first turn, each player in turn order declares whether they
/// will take a mulligan. Raises the first declaration for the starting player; the choice
/// system answers it, takes the mulligans and asks the next player. Returns unchanged when
/// no player may mulligan (a scenario that deals a fixed opening hand).
/// </summary>
[RuleRef("103.5")]
Outcome OpenHands(GameState state);
```

`Game.Create` then reads:

```csharp
public Outcome Create(GameSetup setup) =>
    Engine.Zones.Create(setup, Store).Then(Engine.Turn.OpenHands).Then(Engine.Turn.Begin).Then(Settle);
```

`OpenHands` builds the declaration with the helper E13 already exposes, so the option ids, the
kind and the context keys are in one place:

```csharp
// MtgEngine.Rules/Choices/ChoiceSystem.Resume.cs
public static PendingChoice Declaration(GameState state, PlayerId player, int taken, int handSize);
public static ChoiceContext MulliganContext(int taken, int handSize);
```

i.e. `log.Add(new ChoiceRequested(ChoiceSystem.Declaration(state, starting, 0, setup.OpeningHandSize)))`.

**The contract E13 implements on the other side of it:**

| | |
|---|---|
| kind | `"mulligan"` (`ChoiceKinds.Mulligan`) |
| options | exactly two: id `"keep"` and id `"mulligan"` |
| min, max | 1, 1 |
| context | `EffectPath = "mulligan"`, `Extra["mulligans"]` = mulligans taken so far, `Extra["handSize"]` = that player's starting hand size |

On `"mulligan"`: the hand moves to the library through `IZoneSystem.MoveAll`, `Shuffle`, then
`Draw(handSize)`, and E13 raises the next declaration with `mulligans` one higher — unless the
opening hand would be zero cards (CR 103.5), when it goes straight to bottoming. On `"keep"`
with `mulligans` > 0 it raises a `"mulligan-bottom"` question over the hand with
min = max = the number taken; answering that moves those cards to the bottom of their owner's
library, in the order answered.

**What is deliberately not implemented, and needs a decision:** CR 103.5 has every player
declare, then all mulligans happen *simultaneously*, and CR 103.5c exempts the first mulligan
in multiplayer and Brawl from both the bottoming count and the limit. E13 resolves one
player's declaration at a time and counts every mulligan. Whoever writes `OpenHands` should
either raise the declarations in turn order and accept the sequencing, or file the
simultaneity as its own request; the 103.5c exemption is a one-line change to the `taken`
passed into `Declaration` and belongs with whoever knows the format (`GameState.Format` is
already there).

## 3. `ZoneReordered` is the only event for "the library was rearranged"

Not a change request, a note for E1 and E9. Bottoming after a mulligan goes through
`IZoneSystem.Move(..., Placement.Bottom)`, one card at a time, so the log carries one
`ObjectMoved` per card rather than one reorder. That is right for zone changes (CR 400.7 makes
a new object each time), but if `MoveAll` ever gains E1's batch semantics — one board for all
of them — the bottoming should move to it unchanged: E13 already builds the whole set of
`MoveRequest`s and calls `MoveAll` once.
