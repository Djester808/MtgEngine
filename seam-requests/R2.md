## 2. What the P-series generator must write to use it

`AbilityIndex` counts **mana abilities alone, from zero**, in the order they appear in the
permanent's current characteristics — not abilities in general. So the generator counts, over the
face's ability list, the `ActivatedAbility`s that CR 605.1a calls mana abilities (an `AddMana` at the
top of `Do` or in a `Sequence`'s steps, no `LoyaltyCost`), and writes the ordinal of the one it
means. Concretely:

- **Omit it** — or write `null` — for a permanent with one mana ability. Every scenario written
  before this wave means exactly what it meant, and the wave-20 tests still pass unchanged; the
  default is the first mana ability, which is what the wave-19 step always took.
- **`AbilityIndex: 1`** for the second mana ability. `7536eb66` (Emergence Zone) and any land that
  prints two of them are this shape.
- **A non-mana activated ability between two mana abilities does not move the number.** An
  `{T}: gain 1 life` sitting at ability index 1 is skipped, so the second mana ability is
  `AbilityIndex: 1` and not `2`. This is deliberate: it is the number the generator can compute from
  the definition it is reading, and it does not change when the engine's ability list does.
- **An ability an effect grants the permanent is counted too**, because the index is read off
  `ICharacteristics.Of` (CR 613.1d) and not off the printed face. A generated smoke scenario stages
  its own board, so it knows what it granted; if a board ever grants a mana ability *before* the
  printed one in the layer order, the number the generator wrote off the face is wrong. No filler
  grants a mana ability today, so nothing in the corpus hits this.
- **A rider is not a separate step.** A mana ability that also drains its controller is still one
  mana ability; naming it runs the rider, and the scenario asserts both the pool and the rider (a
  `ManaPoolIs` and a `Life`, as `A_mana_ability_with_a_rider_runs_its_rider_when_it_is_the_one_named`
  does).

Two failures, both `ScenarioResult.Error` with the rule in the text, so a generator that miscounts
gets a sentence and not a quiet pass on the wrong ability:

- `'<card>' has N mana abilities and the scenario names number M. (605.3)` — the number is past the
  last one, or negative in the sense of naming one that is not there.
- `'<card>' names mana ability -1, and mana abilities are counted from zero. (605.3)` — a negative
  number.
- The wave-20 `'<card>' has no mana ability to tap for mana. (605.1a)` is unchanged, and still what a
  permanent with none says whatever number the step carries.

As R1 § 2 said, these are runner failures and not the engine's refusal channel, so an
`ExpectRefusedStep` around them does not catch them. Unchanged and still not asked for.

## 3. What this does **not** unblock, and what still owns it

`00d8efa6` (Utopia Sprawl) — the third P-series ask, P20 § 4, P21 § 3, P23 § 4 — is **still blocked**,
and not on this. R1 § 3 is unchanged: nothing gives a basic land type its CR 305.6 mana ability, so a
`ScenarioFiller` Forest cannot be tapped for mana at any index. The two roads there are still the two
roads:

- **E-series ask (the honest one):** a permanent with a basic land type gets that type's intrinsic
  mana ability in the layer system, read off the subtype (CR 305.6). Lands the card.
- Or `ScenarioFiller`'s five basics print the ability themselves — mine, still not done, still for
  the same reason: a later intrinsic-ability arm would then double it.

And P23 § 4's other half for that card is unchanged: `Enchant` reads only a `Simple` filter, so
`subtypes: [Forest]` is refused before the tap is reached. That is the interpreter's, not mine.

`7536eb66` (Emergence Zone) is unblocked on the runner's side by this parameter; its second ability
is still an `Unsupported` marker, which is the vocabulary's.

## 4. One reading of CR 605.1a, still asked for

R1 § 2's ask stands and this wave did not change it: `IsManaAbility`/`CouldAddMana` here is a third
copy of the same predicate beside `CastingSystem.ManaAbilities` (private) and `Query.Predicates`
(private, broader). Now that a scenario **counts** mana abilities, the copies disagreeing is worse
than it was: the number a generator writes is computed against this copy's reading, and the casting
system's is what actually resolves. A public reading all three share is still a cross-folder change
no folder here owns.

While reading the rule for that: this copy checks two of CR 605.1a's four criteria (could add mana,
not a loyalty ability) and notes the third (no target) holds by construction. The fourth — **"its
cost and effect don't move any card to or from a library"** — is checked by none of the three copies.
An ability that adds mana and searches a library is a mana ability to all of them and is not one.
No corpus card in the failing set turns on it, so I did not add a fourth arm to a predicate that
should be one reading in one place; it belongs with the ask above.
