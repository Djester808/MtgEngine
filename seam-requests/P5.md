# P5 — seam requests

## 1. `SmokeTests.cs` still calls `Translator.Parse`, so `Translator.cs` cannot be deleted

`Translator.cs` is now empty of everything the stages provide: the prompt, the batch calls, the
collect loop and the repair round are gone, and the pilot uses `TranslationPrompt`,
`AnthropicTranslationClient`, `TranslationStore`, `TranslateStage`, `AgreeStage` and
`CardFileWriter`. What is left is one forwarding member:

```csharp
public static (CardDefinition? Definition, string? Error) Parse(string text) => TranslationPrompt.Parse(text);
```

It exists only because `tests/MtgEngine.Pipeline.Tests/SmokeTests.cs:19` calls
`Translator.Parse(text)`, and that file is not mine to edit. **The change I need:** one line in
`SmokeTests.cs`, from `Translator.Parse(text)` to `TranslationPrompt.Parse(text)` (with
`using MtgEngine.Cards.Pipeline.Translate;`), and then `MtgEngine.Cards.Pipeline/Translator.cs`
deleted outright. Nothing else in the repository references the type.

## 2. `TranslateStage` has no submit-only entry point

`TranslateStage.Run` submits a batch and then immediately polls it to the end in the same call.
That is right for a stage that owns a run from end to end, and wrong for the pilot, whose whole
point is that no process holds the pipeline dll for the hours a batch takes.

So `pilot-submit` submits through `ITranslationClient.SubmitBatch` — the stage's own transport —
and records the batch in the stage's own `TranslationStore` as `StoredBatch(..., Collected: false)`,
which is exactly the record `TranslateStage.CollectPending` looks for. `pilot-collect` then runs
the stage normally and the batch is collected, never resubmitted. No collection, parsing, linting
or repair logic is duplicated; only the two-line submit is.

**The change worth making (P1's file, wave 2):** a
`Task<IReadOnlyList<StoredBatch>> Submit(cards, models, promptVersion, ct)` on `TranslateStage`
that does the submit-and-record half of `Run`, with `Run` calling it. Then the pilot's submit
command is one call and the stage owns every request it makes.

Related, and smaller: `pilot-collect` passes `MaxPolls: 1` so that if the stage ever decides to
submit a fresh batch for a card whose answer was missing, it cannot spin — it polls twice and
throws instead of busy-waiting to `MaxPolls` (2000) with `PollDelay` zero. A collect-only mode on
the stage (submit nothing, evaluate what is stored) would be a cleaner way to say that.
