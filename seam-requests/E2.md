# E2 — seam requests (turn structure and priority)

## 1. `tests/MtgEngine.Rules.Tests/events.txt` needs three lines

`EventLogTests.Every_event_type_is_listed_in_events_txt` compares the file to the assembly, so
adding an event without the line is a red build. The turn system raises three that wave 0 did
not have; all three live in `MtgEngine.Rules/Turn/TurnEvents.cs`, namespace
`MtgEngine.Rules.Events`. Please add, in the file's ordinal order:

```
EndOfTurnEffectsEnded
ExtraTurnTaken
PriorityHandedTo
```

- `EndOfTurnEffectsEnded(ImmutableList<int> Effects)` — CR 514.2 / 611.2a. Carries the ids of
  the `ActiveEffect`s removed so a replay removes exactly what the game removed.
- `ExtraTurnTaken(PlayerId Player)` — CR 500.7. Pops the extra turn from
  `TurnState.ExtraTurns` as it begins. Without it the same extra turn is taken forever:
  `TurnBegan` does not touch the queue.
- `PriorityHandedTo(PlayerId Player)` — CR 117.3d. See 2.

## 2. `PriorityGranted` clears `PassedInSuccession`, so a round of passes cannot be counted

`PriorityGranted.Apply` sets `Priority = new PriorityState(Player, [])`. CR 117.4 ends a step
only when every player passes **in succession**, which is what `PassedInSuccession` records — so
if the mid-round handoff of CR 117.3d uses `PriorityGranted`, the record is wiped on every
handoff and the count never reaches more than one pass. Nor can the handoff be left out: with
`Holder` null, no other subsystem can tell who may act.

What I would like: `PriorityGranted` keeps `PassedInSuccession` (`state with { Priority =
state.Priority with { Holder = Player } }`), and the record is cleared where succession is
actually broken — a step beginning, a resolution, or a player taking an action, CR 117.3c.

Until then the turn system raises its own `PriorityHandedTo` for the mid-round handoff and uses
the seam's `PriorityGranted` only for a fresh round (a step began, CR 117.3a; something
resolved, CR 117.3b), which is the case where clearing is correct. `Holder` is accurate for
every other subsystem either way. If the seam changes, `PriorityHandedTo` and its
`events.txt` line can be deleted in one edit.

## 3. `TurnBegan` does not set `TurnState.TurnOrderIndex`

`TurnBegan.Apply` sets `Number`, `ActivePlayer`, `Step` and `IsExtraTurn`, so `TurnOrderIndex`
keeps whatever it had — 0 for the whole game. The turn system therefore treats the player order
as the turn order (the player at index 0 takes turn 1, CR 103.8, and the next turn goes to the
next `PlayerId` still in the game, CR 104.3) and never reads the field. Either
`TurnBegan` should carry and set the index, or the field should go, before another subsystem
reads a stale 0 out of it.

## 4. Note, not a request: control is the stored controller here

`UntapStep` untaps "the permanents the active player controls", CR 502.3, and clears summoning
sickness, CR 302.6. Control is a computed characteristic (CR 613, `ICharacteristics`), but
`ITurnSystem` is constructed with the zone and casting systems only, so the stored
`GameObject.InitialController` is what this code can read. Once E7 lands, either
`ICharacteristics` joins this constructor or the untap step keeps missing control-change
effects. Flagging it rather than working around it.
