# E14b — the coordinator's two lines in `Engine/Game.cs`

`MtgEngine.Rules/Legal/LegalActions.cs` now takes the combat system as an optional last
constructor argument and asks `ICombatSystem.CouldAttack` / `CouldBlock` instead of re-reading
CR 508.1a, 302.6, 702.10b, 702.3b and 509.1a for itself (wave 3's decision row "E2b, E14 —
`ICombatSystem.CouldAttack`/`CouldBlock`: **Now on the seam**; `LegalActions` still has its own
reading — wave 4 switches it to the seam").

Because the argument is optional, both existing compositions still compile — but a composition
that does not pass it offers **no attackers and no blockers**, which is the honest answer for a
view that cannot read the rule (there is no second reading left to fall back on). So the two
lines have to change, or `Wave1()` and `Wave2()` stop offering attackers.

`combat` is already in scope in both methods, constructed above the `Subsystems` call.

## `Game.cs` line 49, in `Subsystems.Wave1()`

```csharp
            new MtgEngine.Rules.Legal.LegalActions(casting, layers, combat));
```

## `Game.cs` line 82, in `Subsystems.Wave2()`

```csharp
            new MtgEngine.Rules.Legal.LegalActions(casting, layers, combat));
```

Nothing else changes: the constructor is
`LegalActions(ICastingSystem casting, ICharacteristics characteristics, ICombatSystem? combat = null)`.

`Stubs.Combat` still does not implement `CouldAttack`/`CouldBlock` (the seam's defaults throw),
so a composition that uses it must not be asked for attackers. Neither `Wave1()` nor `Wave2()`
uses it — both build a real `Combat.CombatSystem` — so both are safe to wire.
