## 1. Done here — CR 401.5 with 401.6 (answers E9v ask 3, complete)

`PlayerView.RevealedTopCard` (a body property, so no existing construction of a seat moved) and
`ViewProjector.RevealedTop`. While an `ActiveEffect` whose effect is `PlayWithTopCardRevealed`
lists a seat in `AppliesToPlayers` — which is exactly how E9v's interpreter arm creates it — that
library's top card is projected for **every** viewer, through the ordinary `View`, so it carries
its computed characteristics (CR 613.5) like any other object. Without the effect the library
stays a count and nothing else, which is what `A_library_is_a_count_and_never_a_card` has always
asserted and still does.

Three things worth recording, because each was a decision and not a default:

- **It is built once per seat, not once per viewer.** CR 401.5 reveals the card to every player,
  so the viewer is not consulted at all. That is the whole difference from `MayLookAtTopCard`,
  the private half of the same rule, which has **no arm in the projector** and deliberately so —
  a one-player look needs the viewer, and no card in the corpus has asked for it yet.
- **CR 401.6 needed no code.** The rule says a card that stops being revealed and is revealed
  again becomes a new object; the view remembers nothing between projections and shows whichever
  object is on top now, so the new object arrives under the id CR 400.7 already gave it. The test
  moves the revealed card to a graveyard and asserts the next projection carries a different id.
- **An empty library reveals nothing**, and the effect on one seat reveals nothing on any other —
  both tested, the second with a serialised-view assertion that the opponent's deck name is absent,
  the same shape the rest of that file uses.

## 2. Done here — the shape and the projection of the attack tax (CR 508.1d)

`LegalActions.AttackTaxes` (a body property defaulting to empty, so `Legal/LegalActions.cs` and
every other caller compile unchanged), the `AttackTaxOffer(ObjectId Attacker, string Cost, bool
Payable)` record, and `Views/AttackTaxes.cs` — the `IAttackTaxes` seam and `AttackTaxes.For`,
which prices the view's own `EligibleAttackers` list and nothing else.

**The view does not read CR 508.1h.** E4i's own reason is the one taken: a second reading in the
view is the drift the `CouldAttack` seam removed for CR 508.1a, and the total genuinely cannot be
computed here — it is locked in against the declaration being made, the amount inside the cost
counts that declaration, and only `CombatSystem` knows any of it. So `For` asks, collects the
non-null answers in the order the attackers were offered in, forces `Attacker` to the id it asked
about, and offers nothing at all when the game was composed without the seam.

An attacker that owes no tax has no entry (an ordinary combat is an empty list); an attacker whose
tax the engine cannot express as mana is offered with `Payable: false` rather than dropped, because
CR 508.1d makes paying the player's choice and a choice cannot be made from a list that does not
say the price exists.
