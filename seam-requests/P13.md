# P13 — the activation's colour, the crash path's test, and the rulings round rehearsed

No seam change is requested. Everything below is built on seams wave 9 already answered
(`ActivateStep.ManaColors`, `ActivateAbility.ManaColors`) or on a construction inside
`MtgEngine.Cards.Pipeline`, which is P-series work.

## 1. The colour reaches the command (CR 608.2d)

`ScenarioRunner` passes `ActivateStep.ManaColors` to `ActivateAbility.ManaColors`, and
`SmokeActivation` now generates the "add one mana of any colour" activations it used to refuse:
one `"W"` per mana the ability adds, with `ManaPoolIs` asserting the pool it leaves behind. The
pool is stocked to exactly the activation's cost first (`SmokeBoard.PaysActivationExactly`), the
same reading `PaysExactly` gives a cast, because the deep pool would make the assertion meaningless.
A production the step has no field for — a chosen colour, the commander's identity, what a land
could produce, one of a named pair, or more than one mana at once — still gets no scenario.

**This depends on E3h and regresses `verify` until E3h lands.** The casting system still reads the
colour off `command.CostChoices` (`CastingSystem.OneProduction`) and not off `ManaColors`, so the
three cards that now generate such a scenario are refused with "The colour of mana to add was not
chosen" (608.2d). Measured in this worktree over a clean `cards/`:

| | verified | failed | no scenarios | unsupported | crashed |
|---|---|---|---|---|---|
| wave-9 tip | 83 | 0 | 0 | 4 | 0 |
| this branch, before E3h | **80** | **3** | **0** | **4** | **0** |

The three are the same shape and name the same refusal: an artifact that sacrifices a creature for
one mana of any colour, a bird that taps for one, and a land's ability that adds one. They pass the
moment the casting system reads the command; nothing else moved.

`ScenarioRunnerTests.ManaColors.cs` proves the handover with the wave-2 casting system wrapped in a
recorder — the colour on the step is the colour on the command — and its third test reads the play
in a real game without freezing today's gap: it accepts either the 608.2d refusal or a passing run,
so E3h closes the gap without having to delete a test.

`ScenarioRunner.cs` was at 498 lines, so `ParseMana` moved to `ScenarioRunner.Mana.cs` and
`ScenarioRun` is `partial`. The runner file is 463 lines now.

## 2. `VerifyCommand.Crashed` has a test again

`VerifyCommand.Verify` takes an optional `Func<CardDirectory, IScenarioRunner>` and defaults to the
real engine, which is the only runner it ever builds for itself. A test hands in a runner that
throws, and the crash count, the demotion of a card that claimed to be verified, the `CRASHED` log
line and the exception recorded as the first expectation's `Error` are all asserted again. This is
the "honest fix" P12 § 4 asked for; the construction was P-series, so no seam moved.

## 3. The rulings round, rehearsed without credits

Two tests in `VerifyCommandTests`: `RulingsStage.Run` turns a ruling into a scenario through the
fake batch client (submit, poll, validate), and the round end to end — `rulings-submit`,
`rulings-collect`, then `pipeline verify` — proves the stored ruling scenario is kept beside the
generated one and that both are played, so the card's verdict counts two scenarios. Nothing reaches
the network. The stage already took an `ITranslationClient`, so no seam was needed for the fake.
