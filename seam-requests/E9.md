# E9 — the interpreter

## 1. `events.txt` needs three lines (blocking the gate, not this branch)

The interpreter produces three events no wave-1 subsystem had a spelling for. They are declared
in `MtgEngine.Rules/Interpreter/InterpreterEvents.cs`, which is the pattern `Events/GameEvent.cs`
documents ("a subsystem adds events in its own files"), and E2 already followed in
`Turn/TurnEvents.cs`. But `tests/MtgEngine.Rules.Tests/events.txt` is the snapshot of every event
type and is **not** in E9's `owns`, so `EventLogTests.Every_event_type_is_listed_in_events_txt`
will fail on the integration branch until these three names are added, sorted ordinally:

```
ContinuousEffectCreated
DelayedTriggerCreated
ExtraTurnGranted
```

- `ContinuousEffectCreated(ActiveEffect)` — CR 611.2. Nothing in the engine could add an
  `ActiveEffect` before this; `EndOfTurnEffectsEnded` only removed them.
- `DelayedTriggerCreated(DelayedTriggerState)` — CR 603.7.
- `ExtraTurnGranted(PlayerId)` — CR 500.7, the counterpart of E2's `ExtraTurnTaken`.

`InterpreterTests` is green with all three; only the events snapshot is out of date.

## 2. `StackEntry` cannot carry the triggering objects

`IInterpreter.Resolve` is asked to build the context including the remembered "triggering"
objects, but `StackEntry` (`State/GameObject.cs`) has no field for them and `ObjectId` is not
recoverable from `Source` alone: "whenever a creature you control dies, ..." needs the creature
that died, which is not the ability's source.

Requested: `ImmutableDictionary<string, ImmutableList<ObjectId>>? Remembered = null` and
`ImmutableList<ObjectId>? Triggering = null` on `StackEntry`, both defaulted so no existing
caller changes. E6 fills them when it puts a triggered ability on the stack; the interpreter
reads them into `EffectContext.Triggering` and `EffectContext.Remembered["triggering"]`.

Meanwhile the interpreter uses the ability's own source as the triggering object, which is right
for "when this enters" and honestly empty for every other trigger shape.

## 3. `IZoneSystem.CreateToken` and the defender (deferred from wave 1, DECISIONS row E1)

The decision was that E9 would change `CreateToken(..., bool attacking)` to take a
`CombatTarget?` because the interpreter is the only caller that knows the defender. It is **not**
needed yet: `Cards.CreateToken` carries only `bool Attacking`, so there is nothing in the
vocabulary to pass. The interpreter passes the bool through. Raise it again with the first
"create a token attacking that player" primitive, which is a vocabulary change too.

## 4. Not requested, recorded

`EffectContext` has no field for the chosen modes, so `Resolve` puts `StackEntry.Modes` into
`Chosen["modes"]` as a comma-separated list and `ChooseMode` reads it there. That works and needs
no seam, but a nested `ChooseMode` would reuse the key. If E13 wants a cleaner locator, an
`ImmutableList<int> Modes` on `EffectContext` is the shape.
