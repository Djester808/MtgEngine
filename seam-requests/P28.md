## 1. Ask — the verify write is refused by the re-translation rule (`Agree/**`, CR 602.2)

E3q § 2's observation, measured. Flusterstorm `86bf58f2` reads `"status": "Verified"`,
`passed 1/1` from run `verify-20260908T042913-3e3c94`, and its stored scenario carries four
expectations (`InZone`, `InZone`, `ZoneCount`, `StackEmpty`) while the run that failed it played a
regenerated one carrying a fifth. **Neither of E3q's two candidates is the defect and the third is:
the verdict is written and the writer refuses it.**

`VerifyStage.Verify` does exactly what it should — a card that was Verified and now fails goes back
to `Translated`, carrying the scenarios that ran — and hands the file to `CardFileWriter.Write`.
`CardFileWriter.Lowers` (`Agree/CardFileWriter.cs:101`) then returns `KeptVerified`, because the
incoming status is `Translated`, the existing is `Verified`, the oracle hash is unchanged and no
`Unsupported` marker is on the definition. That rule exists to stop **a re-translation** undoing a
verification, and it is right for that caller. A verification run is the opposite caller: it is the
only thing entitled to change a verification, and it is the one being refused. The two rules are
each documented in their own file and they contradict.

So the file keeps the old run's scenarios, the old run's engine hash and its `1/1`, and the failure
exists only in a log. That is how a card can be reported failing and read Verified in the same wave,
and it is why the on-disk no-scenario list (84 at the wave-27 tip, P27 § 4) has always been a
superset of the one verify reports.

**What closes it (`MtgEngine.Cards.Pipeline/Agree/**`, one predicate):** `Write` must be able to
tell a verification from a re-translation. Either an argument on the call — `Write(file, lint,
verification: true)` — or, without a new parameter, `Lowers` yielding when the incoming file carries
a `Verification` newer than the existing one at a different engine hash. `Verify/**` cannot do it
from its side: `CardFileWriter` is sealed, `VerifyStage` takes it concretely, and writing `cards/`
from a second place is the one thing that file says must never happen.

**Built here in the meantime, so the disagreement is never silent again.** `VerifySummary` carries
`Stale`, and a run that fails a card whose write was refused prints

```
  STALE FILE    <name> (<id>) 0/1: the file on disk still reads Verified — this run's verdict was refused
```

with the count in the summary line beside verified/failed/unsupported/crashed. Two tests pin it
(`VerifyCommandTests.Wave29.cs`): the same failing runner over a **Verified** file is stale and the
file on disk keeps its old run id, and over a **Translated** file writes and is not — so the count
is about the refusal and not about failing. Falsified by removing the `KeptVerified` check: the
first test then reads 0 stale with the file still claiming the earlier run.

## 2. Done — Brainstorm `36cd2364` and Demand Answers `c11e84a1`, both verify

Checked on the cards, engine `0f74a03de66e7d38`: `verify cards --only` reports
`verified Brainstorm 1/1` and `verified Demand Answers 1/1`. The rewritten card files and their
`.lint` siblings are left unstaged.

**Brainstorm — `ZoneCount was 4`, and 4 was right.** "Draw three cards, then put two cards from your
hand on top of your library" is a `Sequence` of a `Draw` and a `Move` of a `Choose` out of the hand;
only the `Draw` was read, so the generated hand was `HandSize + 3` where the play left
`HandSize + 1`. The road (`SmokeScenario.Remembered.cs`) reads
`Move { What: Choose { Among: null, Chooser: You, Count: Fixed }, To: Library }` whose filter is
the hand and nothing else, and moves the two counts against each other (CR 401.1 with CR 121.1).
Which cards went back is not named — the choice is the resolution's player's, and a library's order
is not a zone a scenario can read.

`SmokeBoard.HandHolds()` is called with it, and `SmokeBoard.Empty` now yields to it: **a draw and a
put-back that cancel** (draw two, put two back) move four cards and leave every count where it
started, and the board had nothing to say, so no scenario was generated at all. That is the same
argument `LifeHolds` was built on. Three tests, one of them the falsifier (the same card without the
put-back still counts the whole draw, so the two shapes cannot collapse into one).

**Demand Answers — "None of the costs offered can be paid (601.2h)", and the board had stocked
nothing.** `ChooseCost` fell through `SmokeScenario.Costs`'s `default` arm: no artifact was stood for
the sacrifice, and the discard behind it is refused by `ObjectCosts.Choose` when the cast names no
card (E3q § 1 — no object is ever picked for the player), so **every** option was unpayable.
`Costs` is now `Stocks`, one cost at a time, and a `ChooseCost` stocks **its first option and only
its first** (CR 601.2b): E3q's `CostPayment.Chosen` pays the first payable option in printed order,
so stocking two of them would leave the play free to take either and the counts could not say which
one it took. Three tests: the artifact is stood and named, the same two options reversed stock the
hand and stand nothing, and a first option the board cannot stock gets **no** scenario rather than
one that quietly relies on the second.
