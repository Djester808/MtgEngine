# R1 — the scenario runner taps a land for mana (CR 605.3a, 106.4)

Wave 20. `TapForManaStep(Player, Card, ManaColors)` is in `MtgEngine.Cards/Scenarios.cs` with its
`JsonDerivedType` registration beside `AddManaStep`, and the runner turns it into the
`ActivateAbility` of the permanent's first mana ability. Five tests in
`tests/MtgEngine.Rules.Tests/ScenarioRunnerTests.TapForMana.cs`; the whole Rules project is green
(887 passed).

## 1. The schema snapshot has to be regenerated — coordinator's, not mine

`tests/MtgEngine.Cards.Tests/SchemaSnapshotTests.The_committed_schema_matches_the_build` fails on
**both** parameters after the new derived type:

- `cards/schema/scenario.schema.json`
- `cards/schema/card-file.schema.json` (a card file carries its scenarios, so the step list is in it too)

Both committed files list the ten step kinds and none of them names `TapForManaStep`; nothing else
about them changed. The fix is `UPDATE_SCHEMA=1` on the Cards tests and a commit of the two files.
Neither the test file nor the two snapshots are in my manifest, so I left them alone.

## 2. Which ability the step activates, and why the runner picks it rather than the scenario

The brief's shape was `TapForManaStep(player, card, abilityIndex)` in P20 § 4; what landed takes no
index. A generated scenario would have had to count the ability out of a face it never reads, and an
index would have been wrong the moment an effect granted the land another ability. The runner reads
the object's **current** abilities through `ICharacteristics.Of` (CR 613.1d) and takes the first
`ActivatedAbility` that CR 605.1a calls a mana ability — could add mana (an `AddMana` at the top or
in a `Sequence`'s steps), no loyalty cost; the step announces no targets, so 605.1a's third
condition holds by construction. That reading is a third copy of the same predicate: the casting
system has `CastingSystem.ManaAbilities.IsManaAbility`/`CouldAddMana` (private) and the query has
`Query.Predicates.IsManaAbility`/`Produces` (private, and broader — it walks `If` and `May` too).
**Ask, if it is wanted:** one public reading of CR 605.1a that all three share. I did not add one —
it is a cross-folder change and no folder here owns it.

A permanent with no mana ability is a step the game cannot take, so the runner fails the scenario
with the rule in the message (`'<card>' has no mana ability to tap for mana. (605.1a)`) rather than
activating whatever ability happens to sit at index 0. It is a `ScenarioFailure`, so it lands in
`ScenarioResult.Error` and **not** in the engine's refusal channel: an `ExpectRefusedStep` wrapping
it would not catch it, because the runner never got as far as building a command. If a generator
wants that refusal to be assertable, `ExpectRefusedStep` would have to admit a runner failure too —
not asked for here.

## 3. Nothing gives a basic land type its CR 305.6 mana ability

`ScenarioFiller.Plains`/`Island`/`Swamp`/`Mountain`/`Forest` carry only the type line, on the note
that "the intrinsic mana ability is CR 305.6 data the engine already reads off the subtype". It does
not: `Layers.cs` builds `Characteristics.Abilities` from `face.AbilityList` plus layer-6 grants, and
no arm anywhere adds `{T}: Add {G}` for a Forest. So **a filler basic land cannot be tapped for
mana** — `TapForManaStep` on one is refused by § 2's rule, correctly.

My tests therefore use a test-local basic land that prints the ability. The card the step exists for
(`00d8efa6`, an Aura on a Forest) needs a Forest that actually taps for `{G}`, so the generator's
half of P20 § 4 is still blocked on one of two things:

- **E-series ask:** a permanent with a basic land type gets that type's intrinsic mana ability
  (CR 305.6), read in the layer system off the subtype the way `LandTypes.Basic` is read elsewhere.
  This is the honest fix and it lands the card.
- **Or**, cheaper and only good enough for a smoke scenario: `ScenarioFiller`'s five basic lands
  print the ability themselves. That is mine to do and I did not — it would make the fillers assert
  something CR 305.6 says the rules grant, and a later intrinsic-ability arm would then double it.

## 4. What the step does not decide

`TapForManaStep` puts the land's own mana in the pool beside whatever the trigger adds, in whatever
order the game runs them; the step says nothing about that, and a generator writing `ManaPoolIs`
for `00d8efa6` still has to name the total of both. P20 § 4 called that out and it is unchanged.
