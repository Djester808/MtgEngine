# V4 — seam requests

## 1. `Rules/Query`: the query layer owes `AnyTarget` an arm

`MtgEngine.Cards/Selectors.cs` now carries the selector CR 115.4 names:

```csharp
[RuleRef("115.4")]
public sealed record AnyTarget(Amount? Count = null, bool UpTo = false, string? Key = null) : Selector;
```

It is registered under `Selector`, in the committed schema, lint clean, and the canonical pass
collapses both long spellings of the phrase into it (`CanonicalTests.AnyTarget.cs`). The half that
is **not mine** is the engine's: the query layer has no arm for it, so a card file carrying
`AnyTarget` resolves to nothing today.

**The arm, exactly.** `AnyTarget` resolves the way `Target` does — the same targeting rules, the
same `Count`/`UpTo`/`Key` handling, legality re-checked on resolution (CR 608.2b) — with the
CR 115.4 filter: a target is legal when it is a creature, a planeswalker or a battle on the
battlefield, **or** a player. So:

- objects: `new ObjectFilter(AnyTypes: CardType.Creature | CardType.Planeswalker | CardType.Battle)`,
  the filter `Target` would have been given;
- players: every player, the `PlayerFilter.Any` half — no opponent restriction, no "up to".

Both halves are one choice made as the spell or ability goes on the stack (CR 601.2c). The chosen
target rides in the command the way each half already does: an object in `Command.Targets`, a player
in `Command.TargetPlayers`. Nothing new is needed on the command — that is why the record has no
player field, and it is what the doc comment tells the translator.

**The interpreter's side (E9d, not asked for here).** `DealDamage` whose `To` is `AnyTarget` leaves
`ToPlayer` null by construction: the canonical pass removes a `toPlayer` written beside it. So
`DealDamage` must deal its damage to whichever half the stack entry holds, rather than reading
`ToPlayer` for the player case. A reading that still writes both halves is a card that names two
different things to damage, and that one keeps the old behaviour.

**Where `AnyTarget` appears.** `DealDamage.To` today. It is a `Selector`, so anything taking one can
carry it; the phrase itself is only ever printed on damage and on a handful of "target" riders, and
`DealDividedDamage.Among` is the next likely place (CR 601.2d) — the same arm serves it.

## 2. Noted, not requested: `PlayerRestriction` has no `Win` or `GainLife` member

The wave-4 decision reads "`PlayerCant` of exactly Lose, GainLife or Win collapses to
`CantLoseGame`, `CantGainLife`, `CantWinGame`". `PlayerRestriction`
(`MtgEngine.Cards/Continuous.cs`, not mine) has four members: `LifeTotalChanges`, `Lose`,
`BeTargeted`, `BeDealtDamage`. There is no `Win` and no `GainLife`, and `LifeTotalChanges` is
**not** `CantGainLife` — CR 119.1, it also forbids losing life and setting a life total. So exactly
one collapse exists to write, `Lose` → `CantLoseGame`, and that is what landed;
`CanonicalTests.A_restriction_no_single_record_says_stays_a_player_cant` is the negative half.

No change is wanted: `CantWinGame` and `CantGainLife` are already the spelling for their sentences
and the reference now says so, so nothing should ever be written as a `PlayerCant` of them. If a
flag is ever added to the enum, `Canonical.SpecificPlayerRestrictions` is the one-line map it joins.

## 3. Noted, not requested: `StaticAbility.Players` beside a record that names its player

`CantLoseGame`/`CantWinGame`/`CantGainLife` each carry `Who`, and `StaticAbility` carries `Players`.
A reading that sets both and one that sets only the record still differ, and the collapse
deliberately does not touch the parent's field — removing something the layer system is going to
read is the failure mode this repo has already paid for. If E7b decides `Players` is redundant when
the effect names a player, say so and the canonicaliser will strip a `players` of `You` there.
