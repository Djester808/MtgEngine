# V8 — wave 13 vocabulary: what each new record needs from the engine

Every item below landed in `MtgEngine.Cards` this wave, is in its base's name table where a base is
involved, lints where its value can be nonsense, round-trips in `VocabularyAdditionsTests.Wave13.cs`,
and has a one-spelling line in `TranslationPrompt.LaterSpellings`. `IrVersion` is unchanged at 1:
every addition is an optional field or a new derived type, so a card file written last wave still
reads. The schema snapshots under `cards/schema/` are regenerated.

None of these is played by anything yet. Each line names the arm that has to read it.

| Record | Arm that must read it | What it has to do |
|---|---|---|
| `ManaProduction.LandCouldProduceOf: ObjectFilter?` | interpreter (mana) | When `LandCouldProduce` is set, survey the lands the filter admits instead of the lands the controller controls (CR 106.1). A filter admitting no land produces no mana and is not an error. |
| `ManaProduction.ChosenColorKey == "tapped-for-mana-color"` | triggers, interpreter (mana) | Doc only, no new record: every `TappedForMana` firing must store the colour the permanent was actually tapped for under that literal key on the stack entry's `Chosen`, whatever `OfColor`/`OfChosenColorKey` say. Wave 10 already writes the key for the chosen-colour road (E6d/E9i); this asks that it be written for **every** firing, including one with no colour restriction, so "add one mana of any type that land produced" reads it. |
| `ManaProduction.ColorsOfRemembered: string?` | interpreter (mana), choices | One mana of any of the colours of the objects remembered under the key (CR 105.2). The player chooses among exactly those colours; a remembered object with no colour offers none, so the question must not be asked with an empty option list — EINT4's gap (2) is the precedent. |
| `SacrificeCost.RememberAs`, `DiscardCost.RememberAs`, `ExileFromZoneCost.RememberAs` | casting / activation cost payment | The payment stores the objects it took under the key, as they last existed (CR 608.2g, last known information for a sacrificed permanent), so the effect's `Remembered` selector finds them. The key must be visible to the ability's own resolution, i.e. written into the same store the interpreter's `Remembered` reads. |
| `UnsupportedContinuous(Reason, Text)` | interpreter (static abilities), pipeline verify | Refuse by name the way `Unsupported` does after wave 9 (CR 608.2) — never throw — and the pilot must count a card carrying one as "unsupported" rather than running it. It lints L001, so no clean file holds one. |
| `IsRemembered(Key): Predicate` | query | The candidate is one of the objects remembered under the key (CR 603.10). Needs the remembered store in the filter's evaluation context, which the query does not have on every road today — that is the real work in this row. Off a resolution (a static ability's filter) nothing is remembered and it matches nothing. |
| `ObjectFilter.ManaCostIs: IReadOnlyList<string>?` | query | Match the object's **printed** mana cost string against the list, "any of" (CR 202.1). Printed, not derived: a cost-modifying effect does not change it, and an object with no printed cost matches nothing. `ICharacteristics.PrintedOf` (wave 9, E0e) is the reader. |
| `ObjectFilter.NotInCommanderIdentityColors: bool?` | query | True admits an object with a colour outside the controller's commander's colour identity, false admits one wholly inside it (CR 903.4). This is the narrow spelling the wave-10 table deferred as `ColorSetRef`; a bool is additive and does not move `IrVersion`, where a colour-set *reference* in every `Color?` position would have. Outside a Commander game the identity is empty, so true admits every coloured object and false admits only colourless ones — say which the engine does, because the pilot's card is a Commander card. |
| `ActivatedAbility.PayOnlyWithChosenColorKey: string?` | casting (cost payment), mana | The third reading of the one spend rider (CR 106.6b, bitten at CR 601.2h): the mana spent on this activation must be of the colour this object chose under the key. `PayOnlyWith`'s colour check is the same code with the colour looked up from `GameObject.Chosen` instead of the record. L016 now lints all three riders as one-of-three. |
| `KeywordAbility.RememberAs: string?` | keyword expansion (hideaway and friends) | The keyword's exile stores what it set aside under the key (CR 702.75a) so the permanent's other ability can name it with `Remembered`. The store has to outlive the trigger's resolution, because the ability that plays the card is activated later. |
| `Search.OthersTo: Zone?`, `Search.OthersTapped: bool` | interpreter (search) | One search of up to `UpTo` cards (CR 701.23a — one action over one look), the first card found to `To` with `Where`/`Tapped`, every other card found to `OthersTo`, tapped only when it is the battlefield. Two searches is the wrong shape: it looks twice and shuffles twice. |

## Decisions taken here

- **`IrVersion` stays 1.** Nothing this wave is breaking. `ObjectFilter` gained two optional fields
  before `Also` rather than after it, which is a source-compatible change only because nothing
  constructs the record positionally past its first few parameters; the JSON is by name.
- **`Protection.OfNotInCommanderIdentity` was not added.** `.agents/briefs/wave13.md` proposed it and
  the brief proposed `ObjectFilter.NotInCommanderIdentityColors`; the filter field is the one that
  landed, because protection is written as a `KeywordAbility` whose `Of` is an `ObjectFilter`, so the
  filter field spells the protection card **and** every other "colors not in your commander's color
  identity" clause. A second field on a protection record would have been a second spelling of one
  idea.
- **The L016 pair rule was replaced, not doubled.** The wave-8 rule that errored on `PayOnlyWith`
  beside `PayOnlyFrom` is now a count over all three riders, so one defect still raises one finding.
- **New lint codes**: L018 (`ManaCostIs` empty, or an entry that is not a printed symbol string),
  L019 (`Search.OthersTapped` outside the battlefield; `OthersTo` equal to `To` is a warning),
  L020 (`LandCouldProduceOf` with no survey; `ColorsOfRemembered` beside another colour choice or
  with an empty key). `UnsupportedContinuous` reuses L001 as briefed.
- **`IsRemembered` is a key consumer**, so it is in the linter's `IsConsumer` set and its key is
  checked by L003 like `Remembered`'s. A filter naming a key nothing on the face produces is an
  error, not a silently empty match.

## Not done in this box

- Row 12 of `.agents/briefs/wave13.md` (`Choose.Among: Remembered` — choose a subset among remembered
  revealed cards, where opus spelled it with ForEach+If+May(Move) and sonnet gave up). Not in this
  brief's numbered list and not decided: it needs a ruling on whether the existing ForEach spelling
  is the one spelling before a record is added.
- Row 13 (the `TotalAmong`/`GreatestAmong` inner binding doc — the candidate is bound as Source, so
  `Self`). A one-paragraph doc addition on `Amounts.cs`, still owed; it changes the reference the
  translator reads, so it belongs with the next prompt refresh.
- `.agents/briefs/wave13.md`'s engine note that `Query.Predicates.cs:37`'s `AttachedTo` direction
  looks inverted. The vocabulary side is now unambiguous — `AttachedTo(Self)` in a filter means "an
  attachment on this permanent", and "equipped creature" is the `Attached` **selector** — so the
  engine's predicate should be read against that doc and tested (E0-series). If the engine currently
  implements the other direction, the engine is wrong, not the doc.
